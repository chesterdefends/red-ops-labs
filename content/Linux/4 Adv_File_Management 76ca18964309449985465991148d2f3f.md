## Modify Permission Bits Using Symbolic Form

- Symbolic notation uses a combination of letters: **ugo** (referred to as permission classes) and **rwx** (permission bits)
- u = user (owner)    || r = read
g = group                || w = write
o = other (public)  || x = execute

and symbols: +, -, =

ex:

`chmod u+x <filename> -v`

This command will modify permission of the ‘user’ (u—owner) to be able to execute the file — ‘-v’ will print the result/change onto the page.

ex: 

`chmod g-w, o-wx <filename> -v`

This command will revoke write (w) bit from the group (g) members, and will also revoke write & execute bits from public (o) permission class—the command allows for multiple actions in the same command. 

## Modifying Access Permissions

- The octal notation uses three-digit numbering system ranging from 0 to 7 to express permissions for the three user classes.
- Position one (on the chart below) rep: Octal value (0-7)
- Position two rep: Binary notation (000-111)
- r   w   x         r   w   x
0   0   0        1    1    1
-    -    -        +  +   +
- Each “1” corresponds to an r, w, or x, and each “0” corresponds to the hyphen character (-)
- Where ever a 0 is denoted = permission revoked
- Where ever a 1 is denoted = permission granted

## Calculating Default Permissions

- Linux assigns default permissions to a file or directory at the time of its creation
- They are calculated basked on the *umask* (user mask) permission subtracted by a preset *initial* permissions value
- umask = 3 digit octal/symbolic notation that refers to rwx permission for ugo. It’s purpose is to set default permissions on new files and directories without touching permission on existing files and directories.
- Default umask = 0022 (first zero is insignificant)

ex: 

initial permissions:  666 

- umask:                     022

  644:                

6 = u = rw-
44 = go = r--

Above example is an indication that every new file file will have read, write, and execute permissions assigned to the owner, and read and execute permissions to the owning group and everyone else.

## Special File Permissions

1. **setuid** 
- Is set on binary executable files (commands—like su and sudo) at the file owner level and with this bit set, the file is executed (command is executed) by non-owners w/ the same amount of privileges as that of the file owner
- Denoted by an “s” in the owner’s permission class

`[user1@server1 ~]$ ls -l /usr/bin/su
-rw**s**r-xr-x. 1 root root 56936 Feb  7  2023 /usr/bin/su`

To change this capability: 

Revoke: 

`chmod -v u-s /usr/bin/su`

Grant:

`chmod -v u+s /usr/bin/su`

1. **setgid**
- The setgid is set on binary executable files at the group level and with this bit set, the file is executed by non-owners with the exact same privileges as that of the group members
- Denoted by an “s” in the group’s permission class

`[user1@server1 ~]$ ls -l /usr/bin/write
-rwxr-**s**r-x. 1 root tty 23800 Feb  7  2023 /usr/bin/write`

- set the group ID (GID) (ex. 9999) on group-shared directories to allow for files &/or directories underneath to automatically inherit the directory’s owning group. This saves group members who are sharing directory contents from changing the group ID for every new file and subdirectory that they add.  The standard behavior for new files and subdirectories is to always receive the creator’s group.

To change this capability:

Revoke:

`chmod -v g-s /usr/bin/write`

Grant:

`chmod -v g+s /usr/bin/write`
